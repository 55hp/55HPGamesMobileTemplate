# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project overview

A modular, production-ready Unity template (Unity **2022.3.62f3**) for mobile games (hypercasual → mid-core). The template provides a service-registry architecture, an async game state machine, additive-scene bootstrap, a layered UI system, and an Addressables-driven content pipeline. New games are meant to be built on top of it without rewriting the foundation.

Full architecture docs live in `Assets/Documentation/`:
- `README 📘 55HP Games — Unity Mobile Template.md` — overall architecture (bootstrap, services, FSM, addressables conventions)
- `README 🎨 UI & Audio Architecture — Complete Guide.md` — UI layers, navigation/popup/overlay/toast services, audio/music pipeline

Read those before making structural changes — they are the source of truth for intended architecture and are more detailed than this file.

## Working in this repo

This is a Unity project, not a CLI-buildable project in the usual sense. There are no npm/make/gradle build or test commands to run from the shell:

- **Build / Play**: open the project in Unity Editor 2022.3.62f3.
- **Tests**: run via Unity's Test Runner window (`Window > General > Test Runner`), which executes `Assets/Tests/EditMode` and `Assets/Tests/PlayMode`. There is no headless CLI test command configured in this repo — don't invent one.
- The `.csproj`/`.sln` files at the repo root are generated by Unity/Rider for IDE tooling (IntelliSense) — do not hand-edit them; they regenerate from Unity's asmdef files.
- After editing C# scripts, there's no separate compile step to invoke from the shell; Unity compiles on focus/domain reload. Verify correctness by reading the code carefully (matching interfaces, namespaces, service registrations) rather than assuming a build will catch it.

## Assembly / module layout

Each folder below is its own asmdef and compiles as a separate assembly — respect these boundaries when adding references (lower layers must not depend on upper layers):

- `Core.Runtime` (`Assets/Core/Runtime`) — the template engine: architecture, services, save, input, UI abstractions, pooling, gameplay helpers. Namespace root: `hp55games.Mobile.Core.*`.
- `UI.Runtime` (`Assets/Core/Runtime/UIScripts`) — concrete UI runtime (navigation, popups, overlays, toasts, HUD).
- `Core.Editor` / `Core.Runtime.CommandSequence.Editor` — editor-only tooling.
- `Game.Content` / `Game.Features` (currently under `Assets/FlappyTsunami/`) — project-specific gameplay content/features that sit on top of Core. The docs describe this layer as living under `Assets/Game/`; in the current working tree it's still under the demo game folder `FlappyTsunami` (a prior cleanup commit references removing "FlappyTsunami contamination" from the template — check `git log`/current state before assuming which convention applies when adding new game-specific code).
- `hp55games.Tests.EditMode` / `hp55games.Tests.PlayMode` (`Assets/Tests`) — test assemblies, kept separate from game scenes/content.

## Core architecture

### Service Registry (mini-IoC, no singletons)

`ServiceRegistry` (`Assets/Core/Runtime/Architecture/ServiceRegistry.cs`) is a static type-keyed dictionary. Services are registered once in `ServiceRegistry.InstallDefaults()` and resolved anywhere via:

```csharp
ServiceRegistry.Register<T>(instance);
var service = ServiceRegistry.Resolve<T>();
ServiceRegistry.TryResolve(out ITimeService time);
```

Default-installed services include `ILog`, `IEventBus`, `IConfigService`, `ISaveService`, `ITimeService`, `IContentLoader` (Addressables), `IGameStateMachine`, `IObjectPoolService`, `IUIOptionsService`, `ILocalizationService`, `IGameContextService`, `IInputService`. UI-layer services (`IUINavigationService`, `IUIPopupService`, `IUIOverlayService`, `IUIToastService`, `IMusicService`) are installed separately by `UIServiceInstaller` when the `91_UI_Root` scene loads — they are not available until that scene is present, so code that resolves them must run after bootstrap, not before.

### Bootstrap flow (always starts here)

`GameBootstrap` (`Assets/Core/Runtime/Bootstrap/GameBootstrap.cs`), attached in `Scenes/00_Bootstrap`, runs a strict sequence:
1. `ServiceRegistry.InstallDefaults()`
2. Load `SceneFlowConfig` via Addressables and register `ISceneFlowConfig` — must happen before any scene with a `SceneFlowServiceInstaller` loads.
3. Additively load `Scenes/Additive/90_Systems_Audio.unity`
4. Additively load `Scenes/Additive/91_UI_Root.unity`
5. Additively load `Scenes/01_Menu.unity` and set it active

UI-dependent code should wait on `UIRuntime.ServicesReady` (set by `UIServiceInstaller.Awake()` calling `UIRuntime.MarkServicesReady()`) rather than assuming services exist immediately after scene load.

### Game State Machine (FSM)

`IGameStateMachine` / `GameStateMachine` (`Assets/Core/Runtime/Architecture/GameFSM/`) drives async, cancellation-safe state transitions:

```csharp
await fsm.ChangeStateAsync(new GameplayState());
```

Each `IGameState` implements `EnterAsync(CancellationToken)` / `ExitAsync(CancellationToken)`. Only one transition runs at a time — a new `ChangeStateAsync` call cancels the in-flight one via a shared `CancellationTokenSource`. Built-in states: `MainMenuState`, `GameplayState`, `PauseState`, `ResultState` (`Assets/Core/Runtime/Architecture/States/`).

### Scene flow

`ISceneFlowService` / `SceneFlowService` (`Assets/Core/Runtime/Architecture/SceneFlow/`, config in `Assets/Core/Runtime/SceneFlow/`) coordinates target-scene loading, ensures the UI Root exists, shows overlays during loads, and triggers FSM changes. Scene names/paths for flow are driven by the Addressable `SceneFlowConfig`, not hardcoded, so new scenes should be wired through that config rather than string literals scattered in states.

### UI system

Layered, Addressables-loaded, fully decoupled from gameplay. `UIRoot` (in `91_UI_Root`) exposes layer transforms; each service only touches its own layer:

- `Layer_Pages` ← `IUINavigationService` (`PushAsync`/`PopAsync`, stack-based)
- `Layer_Popups` ← `IUIPopupService` (`OpenAsync`/`CloseLastAsync`/`CloseAllAsync`, modal + scrim)
- `Layer_Overlay` ← `IUIOverlayService` (`FadeIn`/`FadeOut`/`ShowLoading`/`HideLoading`)
- `Layer_Toasts` ← `IUIToastService` (`ShowAsync`, auto-pooled/expiring)
- `Layer_HUD` ← HUD widgets

UI pages implement a lifecycle of `OnNavigationIn()` / `OnNavigationOut()` / `OnNavigationReplaced()`. All UI prefabs are loaded by Addressables address, referenced through the generated `Addr` class (`Assets/Core/Runtime/Utils/Addr.cs`) rather than raw strings, e.g. `Addr.Content.UI.Pages.Main_Menu_Generic`.

Navigation pages and popups should inherit `UIPageBase` / `UIPopupBase` (`Assets/Core/Runtime/UI.Abstractions/`) instead of `MonoBehaviour` directly: both expose `Bind(button, action)`, which registers an `onClick` listener and auto-unregisters it in `OnDestroy` (don't hand-roll `AddListener`/`RemoveListener` pairs). `UIPopupBase` also resolves `IUIPopupService` once in `Awake` and exposes `ClosePopup()`, which releases the instance through the service — popups must close via `ClosePopup()`, not by only toggling their own `CanvasGroup` alpha, or the popup service's bookkeeping (and the scrim) goes out of sync with what's on screen. Classes overriding `Awake`/`OnDestroy` must call `base.Awake()`/`base.OnDestroy()`.

### Addressables address conventions

New Addressable entries should follow the existing key layout:

```
content/ui/pages/<PageName>
content/ui/popups/<PopupName>
content/ui/toasts/<ToastName>
content/ui/overlays/<OverlayName>
content/audio/bgm/<TrackName>
content/audio/sfx/<SfxName>
config/main
```

### Audio / Music

`90_Systems_Audio` hosts `MusicPlayer` (two looping `AudioSource`s, `playOnAwake = false`, used for crossfade) and `AudioOptionsBinder`, which routes `IUIOptionsService` volume/mute settings into the Audio Mixer's Music/SFX groups. `IMusicService` exposes `PlayAsync`/`CrossfadeToAsync`/`StopAsync` for BGM addressed under `content/audio/bgm/`.

### Config Catalog (typed gameplay ScriptableObject configs)

`Assets/Core/Runtime/Config/Catalog/` provides a lightweight registry for gameplay-specific `ScriptableObject` configs, distinct from `IConfigService` (the single Addressables-loaded app `GameConfig`). To add a new data-driven config type: implement the empty marker interface `IConfigAsset` on the `ScriptableObject`, place asset instances anywhere under a `Content/` folder, then hit "Scan Content folders" on the `ConfigCatalog` asset's custom inspector (`ConfigCatalogEditor`, editor-only assembly `Core.Config.Catalog.Editor`) to populate it. At runtime, resolve via `IConfigCatalogService.Get<T>()` (single-instance configs; errors if none, warns and returns the first if multiple) or `GetAll<T>()` (multi-instance configs, e.g. one `LevelConfig` per mission). `ConfigCatalogInstaller` registers the service and must sit in a scene that loads before any consumer resolves it (Bootstrap or the menu scene).

### Save & Options

`ISaveService`/`SaveService` (`Assets/Core/Runtime/Save/`) does JSON load/save of a root `SaveData` object containing `PlayerProgressData` (bestScore, highestLevel, lifetimeCoins, extensible). `IUIOptionsService` (volumes, mutes, haptics, language) persists through the same save service — don't build a parallel persistence path for settings.

### Object pooling

`IObjectPoolService`/`ObjectPoolService` + `PooledObject` (`Assets/Core/Runtime/Pooling/`) back the zero-garbage spawn/despawn helpers in `Assets/Core/Runtime/Spawners/` (`TimedPooledSpawner2D`, `DespawnWhenOutOfBounds2D`, `DespawnAfterSeconds`, `ConstantMover2D`). Prefer pooling over `Instantiate`/`Destroy` for anything spawned repeatedly (projectiles, VFX, obstacles) — this is a mobile-perf-sensitive template.

### Haptics, Ads, Analytics (standard mobile-game service seams)

Three additional services follow the same interface-in-folder + `ServiceRegistry` pattern as everything else, giving gameplay/UI code a stable seam to code against even before a real third-party SDK is wired up:

- `IHapticsService` (`Assets/Core/Runtime/Haptics/`) — `Selection()/Light()/Medium()/Heavy()`. Default `HapticsService` respects `IUIOptionsService.Haptics` and calls `Handheld.Vibrate()` (Unity's built-in API can't grade intensity without a native plugin; the graded interface is there so call sites don't need to change when one is added).
- `IAdsService` (`Assets/Core/Runtime/Ads/`) — interstitial/rewarded/banner. Default `NoOpAdsService` always reports not-ready and never grants a reward; it only logs. Swap the registration in `ServiceRegistry.InstallDefaults()` for a real mediation adapter (AdMob, Unity LevelPlay, ...) — no other code changes.
- `IAnalyticsService` (`Assets/Core/Runtime/Analytics/`) — `LogEvent(name, params)` plus `LevelStart/LevelComplete/LevelFail` convention helpers. Default `DebugLogAnalyticsService` writes to the console only.

### App lifecycle (screen wake lock, background auto-pause, Android back button)

`AppLifecycleHandler` (`Assets/Core/Runtime/AppLifecycle/`) is added automatically by `GameBootstrap.Awake()` (`gameObject.AddComponent<AppLifecycleHandler>()`) — no scene wiring needed. It is a plain `MonoBehaviour`, not a `ServiceRegistry` entry, because it only reacts to Unity lifecycle callbacks and resolves `IGameStateMachine`/`ISceneFlowService` on demand each time (not cached in `Awake`, since it's attached before `ServiceRegistry.InstallDefaults()` runs and before `ISceneFlowService` — registered later by a scene's `SceneFlowServiceInstaller` — exists). It handles three things every mobile game needs:
- Sets `Screen.sleepTimeout = SleepTimeout.NeverSleep` for the whole session.
- Auto-pauses (`ISceneFlowService.GoToPauseAsync()`) when the app is backgrounded, but only if `IGameStateMachine.Current is GameplayState` — the existing `SceneFlowService` transition guard makes a redundant call harmless.
- Maps the Android hardware back button (`KeyCode.Escape` in Unity's legacy Input) to Pause from Gameplay, Resume from Pause, and app quit from the Main Menu.

### Event Bus

`IEventBus`/`EventBus` (`Assets/Core/Runtime/Architecture/EventBus.cs`) is the pub/sub layer decoupling gameplay from UI:

```csharp
_bus.Subscribe<ScoreChangedEvent>(OnScoreChanged);
_bus.Publish(new PlayerDeathEvent());
```

Prefer this over direct UI↔gameplay references for cross-cutting notifications (score, death, level, power-ups).

## Conventions to follow

- Namespace root for template code is `hp55games.Mobile.Core.*`; keep new Core-layer types under that root and mirror the existing sub-namespace-per-folder pattern (e.g. `hp55games.Mobile.Core.Architecture.States`).
- No singletons/static mutable state for gameplay/service concerns — go through `ServiceRegistry`.
- Async operations (state transitions, UI navigation, scene flow, music) use `Task`/`async`/`CancellationToken`, not coroutines, except where interfacing directly with Unity APIs that require them (e.g. `GameBootstrap`'s scene-load coroutine, which predates/coexists with the async services).
- Keep test code under `Assets/Tests/EditMode` or `Assets/Tests/PlayMode` — never alongside game/content scenes.
